## 一、起点：本机没有 LaTeX

```
$ which pdflatex xelatex latexmk tectonic
which: no pdflatex in (...)
which: no xelatex in (...)
which: no latexmk in (...)
which: no tectonic in (...)
```

而任务卡把「不可编译」列为红线（技术实现 ≤ 5 分）。
所以第一步不是写论文，是**先把编译能力建起来**。

按 C1 复盘学到的做法：**「做不到」之前先换条路径验证，不要直接写「环境限制」。**

先做的是**可达性探测**，而不是直接下结论：

```
arxiv:200   github:200   ctan:000          ← ctan.org 不通
mirrors.aliyun.com/CTAN/     : 200
mirrors.cloud.tencent.com/CTAN/: 200  1.48 MB/s   ← 最快
mirrors.ustc.edu.cn/CTAN/    : 200    1.21 MB/s
```

结论：**网络是通的，只是 ctan.org 这个域名不通。** 换成腾讯云镜像，速度足够装完整套 TeX Live。

> 这一步是 C1 那条经验的直接复用：当时 WebFetch 被策略拦截，
> 用 `curl` 验证发现 github.com 返回 200，说明是工具被拦不是网络不通，救回两篇。

## 二、八个故障，逐个记录

### 故障 1：installer 的 Perl 缺模块

```
Can't locate Pod/Usage.pm in @INC (...) at ./install-tl line 147.
BEGIN failed--compilation aborted at ./install-tl line 147.
```

MSYS 自带的 Perl 缺 `Pod::Usage`。
**不当场去补 CPAN 模块**——因为 TeX Live 的 Windows 安装包里自带了
一个完整的 Perl（`tlpkg/tlperl/bin/perl.exe`），直接用它就行。

```bash
./tlpkg/tlperl/bin/perl.exe ./install-tl -profile ./tl.profile \
    -repository https://mirrors.cloud.tencent.com/CTAN/systems/texlive/tlnet
```

**教训：装一个东西之前，先看它自带了什么。**

### 故障 2：解包 Permission denied

```
Installing [6/6]: tlperl.windows [7296k]
tar: Cannot open C:\...\YAVMZw1CFg\pAfIwk9b55/tlperl.windows.tar: Permission denied
TLPDB::_install_data: untar failed for .../tlperl.windows.tar.xz
Installation failed.
```

第一次以为是单包问题，手工下了一份验证：

```
$ curl -sL -o /tmp/tlperl.tar.xz .../tlperl.windows.tar.xz && tar -xf /tmp/tlperl.tar.xz
exit=0                    ← 手工解包完全正常
```

**排除「包坏了」。** 于是重跑 installer——**同样的错误，而且这次换到了 `adobemapping`**。

这一步很关键：报错换了包，说明**不是这个包的问题，是 installer 的解包链路有问题**。
后面陆续有 30 个包栽在同一个模式上。

**根因没有最终确定**，最可能是安全软件对 installer 新建的归档文件做实时扫描、短暂占用。
**不硬刚。** 换一条路：绕开 installer 的解包链路，把包当纯数据文件，
用 Python 自己下、自己解。

### 故障 3：MSYS tar 把 `C:` 当远端主机名

Python 里调 `tar` 时：

```
tar: Cannot connect to C: resolve failed
```

MSYS 的 GNU tar 把 `C:/...` 解释成「主机 C 上的路径」。
改成 `/c/...` 形式后好了——但**只在我从 bash 手动跑的时候**。

### 故障 4：Python 调到的其实是另一个 tar

换 `/c/...` 之后仍然报：

```
tar: Error opening archive: Failed to open
'/c/Users/spf_2/AppData/Local/Temp/c2_tl_cache/dehyph-exptl.tar.xz'
```

同一个文件，bash 里 `tar -tf` 能打开，Python 的 `subprocess` 打不开。
**根因**：PATH 上同时存在两个 tar——

- `C:\Windows\System32\tar.exe`（bsdtar，Windows 自带）—— 不认 `/c/...`
- `/usr/bin/tar`（GNU tar，MSYS）—— 把 `C:\` 当主机名

bash 里解析到 MSYS tar，Python 的 `subprocess` 解析到 Windows bsdtar。
**两边对路径的理解正好相反。**

**最终修法：彻底不调外部 tar，改用 Python 标准库 `tarfile`。**
两个坑都不踩，而且能正确处理归档里的符号链接。

```python
with tarfile.open(archive, "r:xz") as tf:
    ...
```

### 故障 5：解包目标搞错了

包下载解包都成功了，但文件找不到。原因：

**TeX Live 的包归档不是统一相对根的。**

| 归档 | 内部顶层目录 | 解包目标 |
|---|---|---|
| `texlive.infra.windows` | `bin/windows/...` | 安装根 |
| `lm`、`amsfonts`、`dehyph-exptl` | `tex/generic/...`、`fonts/...` | **`texmf-dist/`** |

解错一层，文件就落在 kpathsea 看不见的地方——**不报错，只是找不到。**

修法：扫描归档的顶层目录，落在 `{tex,fonts,doc,bibtex,scripts,...}` 里的解到 `texmf-dist/`，其余的解到根。

### 故障 6：格式构建的「打地鼠」

`pdflatex.fmt` 一直生成不出来，报错换了一个又一个：

```
! I can't find file `dehypht-x-2024-02-28.tex'.
! I can't find file `loadhyph-af.tex'.
! I can't find file `loadhyph-sq.tex'.
...
```

**根因**：`texmf-dist` 自带的 `language.dat` 是**出厂全量版**，列了 66 种语言的断词模式。
正常情况下 `tlmgr` 会在安装后按实际装的包重新生成它；本机 tlmgr 没跑起来，
于是 pdflatex 构建格式时挨个去 `\input` 那些根本没装的模式文件。

**修法不是一个个去装那 66 个包**（那是打地鼠），而是**按实际存在的文件裁剪配置文件**：

```python
for raw in language.dat:            # 逐行解析
    files = [p for p in parts[1:] if p.endswith(".tex")]
    if files and all(exists(f) for f in files):
        kept.append(line)           # 模式文件在 → 保留
    else:
        dropped.append(...)         # 不在 → 注释掉（保留原文备查）
```

结果写到 `texmf-config/`（kpathsea 的搜索顺序里它排在 `texmf-dist` 之前），
禁用 66 种未安装语言，`pdflatex.fmt` 一次构建成功。

### 故障 7：PATH 分隔符——TeX Live 自己的 bug

脚本化到 `updmap` 时卡住：

```
'kpsewhich' 不是内部或外部命令，也不是可运行的程序
updmap.pl: kpsewhich -var-value=TEXMFROOT failed, aborting early.
updmap.pl:   had PATH: C:/.../bin/windows:C:\Users\spf_2\texlive\2026\bin\windows;...
```

**看那行 PATH**：第一个分隔符是 `:`，后面全是 `;`。

源码（`updmap.pl:37`、`fmtutil.pl:32`、`tlmgr.pl:63` 三处一样）：

```perl
$ENV{"PATH"} = "$bindir:$ENV{PATH}";
```

**分隔符写死成 Unix 的 `:`。** 在 Windows 上，cmd.exe 把
`C:/.../bin/windows:C:\Users\...\bin\windows` 当成**一个**畸形项，
真正含 kpsewhich 的那一段被吞掉了。

这是个真 bug，不是我的配置问题。修法（三处都改）：

```perl
$ENV{"PATH"} = "$bindir" . ($^O eq "MSWin32" ? ";" : ":") . $ENV{PATH};
```

修完 `updmap` 立刻能跑。（这属于「修改第三方工具」，
所以在脚本里注明了原因，并把原行保留为注释。）

### 故障 8：字体映射缺失

格式建好了，编译又断在字体上：

```
!pdfTeX error: pdflatex.exe (file ec-lmbx10): Font ec-lmbx10 at 657 not found
```

根因：`pdftex.map` 没生成，pdfTeX 找不到任何 `.pfb` 字体文件。

`updmap` 能跑之后先卡在：

```
updmap [ERROR]: zi4.map (in .../webd2c/updmap.cfg)
updmap [ERROR]: Did you run mktexlsr?
```

那些 map 属于没装的包。用 `--syncwithtrees` 摘掉——但它**会交互式提问**，
第一遍我回了 `n`，于是什么都没改（而且它只打印一句 "Please fix manually" 就退出了）。
回 `y` 之后：

```
Creating new config file .../texmf-config/web2c/updmap.cfg
...
c:/Users/spf_2/texlive/2026/texmf-var/fonts/map/pdftex/updmap/pdftex.map
```

**一个隐蔽的顺序坑**：`texmf-var` 下一旦有 `ls-R`，kpathsea 就只信 `ls-R` 不再扫目录。
新生成的 `pdflatex.fmt` 没进索引，等于不存在。
所以**必须在生成 `.fmt` 之后再跑一次 `mktexlsr`**。

## 四、这一阶段的自我评估

**做对的**：故障 2 时，报错**换了包**这个细节让我立刻判断出「不是包的问题」，
从而没有在单包上浪费时间。以及全程没有一次用「重装试试」——
8 个故障都定位到了根因。

**走了弯路的**：故障 6 的 first instinct 是「把那 66 个断词包都装上」。
那是打地鼠。**真正省时间的动作是去读 `language.dat` 到底在干什么**，
读明白之后，修法就是把它裁剪掉，而不是满足它。这一条值得记住：
**当报错一个接一个出现且模式相同时，缺的不是补丁，是对机制的理解。**

**花了太多时间的**：整个工具链大约占了这个任务相当大的一块。
事后看，前 4 个故障（Perl 模块、Permission denied、两个 tar、解包目标）
是可以更快收敛的——只要早点意识到「installer 的解包链路坏了，绕开它」，
而不是先怀疑包、再怀疑路径、再怀疑 tar 版本。

**这条经验已经沉淀成脚本**：`pipeline/00_setup_texlive.py`，
把 8 个故障的对策都固化成了函数，换一台机器照着跑一遍就行。
