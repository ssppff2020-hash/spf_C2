## 维度一 · 目标复盘：要的到底是什么

> **定义**：把「纸面任务」翻译成「可判定的成功标准」。这一步做错，后面每一步都在做错的事。

C1 复盘里最重的一条教训是 **F6：交付形态偏离任务书字面要求**，
对策是「开工前 10 分钟只做任务书逐句对照」。这次第一件事就是这个。

任务卡原文说「产出一篇结构完整、可投稿的 LaTeX 学术论文」，
真正的判分标准在 `rubric.json`。逐条读出来的结果是：

| 维度 | 分 | 读出来的真正要求 |
|---|---|---|
| researchRigor 研究严谨性 | 25 | **引用造假 → 0 分**。文献必须真、论证必须有据、结论必须有边界 |
| technicalExecution 技术实现 | 20 | **不可编译 → ≤ 5 分**。这是硬门槛，先于一切内容质量 |
| artifactCompleteness 产物完整性 | 15 | paper.tex + references.bib 齐全、可独立使用 |
| aiUsage AI 使用质量 | 20 | 多轮迭代、**有日志佐证**、AI 结论经人工核验 |
| reflectionQuality 复盘质量 | 20 | 七维 AAR，**含「AI 误导」案例与对策** |

**三条关键推断**：

1. **40 分（红线相关的 technicalExecution 20 + researchRigor 的引用部分）与「论文写得好不好」无关**，
   而与「能不能编译、引用是不是真的」有关。所以：
   - 第一件事不是写论文，是**把 LaTeX 环境建起来**（本机一个 TeX 都没有）；
   - 第二件事是**给引用设计一条核验流水线**，而不是「查几篇差不多得了」。
2. **任务书自己给出了可接受的贡献形态**：「一个新的分类、一个对比实验、一个可靠性清单」。
   这说明**不需要做出重大理论突破**，一个小而实的贡献就够了。
   这直接决定了选题——不去碰「证明一个新定理」，而是做「分类 ＋ 残余风险分析 ＋ 清单 ＋ 审计」。
3. **「文中所有 AI 生成结论均有人工核验记录」是内容要求**，不只是流程要求。
   所以核验不能是「我心里过了一遍」，必须**落成可指认的产物**。

**事后看，这三条推断都对**，但第四条没预见到（见维度五 F6）：

4. **任务书给了贡献形态，但没给「贡献强度」的下限。**
   我一开始以为「分类 ＋ 清单」就够，后来发现纯思辨的框架撑不住「可投稿」。
   补上实证部分是被逼出来的——**但正因为是被逼的，它反而成了论文最扎实的一块。**
   这条应该早点想清楚：*「可投稿」意味着读者会问「你的证据是什么」*。

## 维度四 · 归因分析：为什么顺利 / 为什么不顺利

> **定义**：区分「运气」和「可复用的方法」。

### 为什么引用核验能真的抓到东西（超出预期）

- **不是运气好，是判据设计对了。** 三条判据（标题相似度 / 第一作者姓氏 / 年份）里，
  **「标题相似度 ≥ 0.90」是唯一能抓到那三条错误的**。
  - 如果只查「编号能不能解析」：错误 1 的编号 `2308.08381` **能解析**，直接混过。
  - 如果只查「标题大概对不对」：错误 2 的相似度是 **0.9217**，落在那个人眼会放过、
    机器阈值也不该卡的区间。
  - 只有**逐字比对**才看得出 `Limited` 和 `Free`、`Theorem Proving` 和 `Program Verification` 的差别。
- **另一个关键决定：核验结果原样落盘，人工不覆盖。**
  因为 v1 的记录留着，才能事后算出「自动标记 5 条 → 真实错误 3 条」
  这个漏斗，也才能发现「核验器自己的 bug」那一条。

### 为什么 Study B 的数字比预想的有价值

- 原本只是想要一个「工件率」。
- 真正有价值的数字是后来才算出来的**查准率 80% / 查全率 61.5%**——
  它说明自动筛选**同时向两个方向出错**，而修复方式是**加人工验证层，不是调阈值**。
- **这不是设计出来的，是「数字必须由脚本生成」这条规则逼出来的**：
  写论文时发现表格和正文口径不一致，回去改脚本重算，才算出了这组数。
  如果我选择「把正文改成和表一致」，就会错过它。

### 为什么环境搭建花了这么久

- 8 个故障，逐个定位到根因，没有一次用「重装试试」。
- **但收敛速度本可以更快。** 故障 2（解包 Permission denied）时，
  第一次报错在 `tlperl.windows`，第二次换到了 `adobemapping`——
  **报错换了包，这是「不是包的问题」的强信号**，我当时抓住了。
  但接下来我在「路径格式」「tar 版本」上绕了两圈，
  才想到正确的解法是**绕开整个解包链路**。
- 根因是一个判断顺序问题：**先怀疑了三个不该怀疑的东西，最后才怀疑主流程本身。**

### 为什么编译能一次通过的只有一部分

- 第一次编译就失败（`! Missing number, treated as zero`，作者栏方括号）。
- 更该记的是**我自己的构建脚本静默失效**：
  `grep -c` 退出码导致计数变量变成 `"0\n0"`，所有健全性检查被跳过，
  脚本却在最后打印「OK」。
- **一个静默失效的检查器比没有检查器更危险**——它给的是假的安全感。

## 维度五 · 失败清单：具体踩了什么

| # | 失败 | 表象 | 根因 | 修复 |

| F6 | **论证层未核验** | 事实层全核，论证层（第 3/7 节的推理）无人工审读 | 把「核验」默认成了「核验事实」，没意识到「AI 提出的框架」也是一个 AI 生成结论 | **未完全修复**；在论文 7.3 节正文中如实声明 |
| F7 | 图注写中文导致渲染告警 | `Glyph 26368 missing from font(s) DejaVu Sans` | 英文论文的图注本就该是英文，一开始没想清楚读者是谁 | 图注全部改英文（并保留 `refs_corrections.json` 的中文原文不动——**记录是证据**） |
| F8 | 让 AI 做文献调研时没要求带标识符 | 第一轮拿回一段散文式综述，其中有内容错误（把 V1/V2 两篇论文的副标题缝合） | 没在一开始就要求「每条都带可核验标识符」 | 第二轮回炉重做，并在写进论文前逐条核验 |

**优先级最高的两条是 F6 和 F2。**

- **F6** 是**流程类**缺陷：我核验了「引用是真的」，但没核验「推理是对的」。
  任务书的字面要求是「**文中所有** AI 生成结论均有人工核验记录」，
  框架本身就是一个 AI 生成的结论。用「核验了事实就等于核验了内容」来替代，
  和 C1 的 F6（用「AI 翻译」替代「机翻＋人工校对」）是**同一种合理化**。
  **C1 的教训在 C2 以另一种形式重演了。**
- **F2** 是**思维类**缺陷：看到结构化字段就想用。
  这类错误在任何「从 API 拿数据」的场景都会重现——
  比如把 OpenAlex 的 `cited_by_count` 当作权威引用数、
  把 GitHub 的 `stars` 当作质量指标。**判据：这个字段是怎么被召回的？**

## 维度六 · 改进方案：下次怎么做得更好

> **定义**：每条都要能落到「下一次的具体动作」。

**针对 F6（流程类，最重要）**

1. **把「核验」拆成两层，并分别声明**：
   - **事实层核验**：引文、数字、代码、编译 → 可自动化。
   - **论证层核验**：推理有效性、结论边界、有没有过度外推 → **必须人工**。
   下次接到任务，**前 10 分钟就在计划里把这两层分别列出来**，
   并明确「论证层由谁、在什么时候、用什么标准检查」。
   → 本次只有事实层，所以在 README 第六节和论文 7.3 节**显式声明了降级**，
   而不是让评审去发现。

2. **给「AI 提出的论点」单独设一道检查**。
   事实层的核验器（`01_verify_refs.py`）拦不住论证层的错误。
   需要的是**对抗性复核**：让一个独立的过程去专门找框架的反例，
   而不是让它去确认框架对不对。
   → 论文 7.2 节已经写了「我们欢迎一个共同尺度的反例」，
   但那是**写给读者的**，不是**做给自己的**。差别很大。

**针对 F2（思维类）**

3. **用任何结构化字段前，先写一句「它是怎么被召回的」**。
   按标题召回的字段（OpenAlex 的会议名）和按主键查的字段（Crossref 按 DOI 反查）
   可靠性差一个量级。
   → 固化为一条编码规范：**凡是从搜索接口来的字段，不得直接进入交付物，
   必须用主键回到权威源复核。**

**针对 F3 / F4 / F5（工程类）**

4. **检查器本身要有自检**。
   `05_build.sh` 这次的 bug 是「检查器坏了但报告 OK」。
   → 动作：给健全性检查加一条**已知会失败的自测**——
   在空文件上跑一遍，确认它真的会报错。**没验证过会失败的检查器不算检查器。**

5. **图表与正文的每一个数字都只允许有一个来源**。
   本次是靠「图读同一份 JSON」解决的，但**表 3 还是手填过**。
   → 动作：**论文里的所有表格也由脚本生成**（LaTeX 表格片段），
   手只写表头与文字。

**针对 F8 / 文献调研**

6. **让 AI 做任何检索类工作，第一条指令就要求带标识符**。
   「列几篇重要工作」这种指令产出的是散文，无法核验；
   「列几篇重要工作，每条给出 arXiv 编号或 DOI」产出的是可核验的清单。
   → 本次第一轮调研因此报废重做。

**可以搬走的（方法层）**

7. **「先写错的，再核验，报错误率」这个模式本身值得复用到别处。**
   它把「AI 可靠吗」这个无法回答的问题，变成了「AI 在这个任务上错多少」这个可以量的问题。
   任何「AI 生成 → 下游当作事实」的环节都可以这么量：标注、抽取、数据清洗、测试用例生成。

## 维度七 · 迁移与复用：换一个题目 / 换一个人怎么用

> **定义**：这次的经验里，哪些与「AI4Math 论文」无关，能搬到下一件事。

**能直接搬走的（放在 `pipeline/` 里）**

| 资产 | 迁移方式 |
|---|---|
| `00_setup_texlive.py` | **本机装 TeX Live 的唯一可行路径**。8 个故障的对策都固化成函数，换台机器直接跑 |
| `01_verify_refs.py` | 换领域只需改 `refs_candidates.json`。三源交叉的逻辑与学科无关 |
| `02_build_bib.py` | 「bib 是生成物」这个机制本身可搬；换领域只需调 venue 处理 |
| `03_corpus_audit.py` | Study A 的部分完全通用（任何「AI 生成清单 ＋ 核验」都能套）|
| `05_build.sh` | 编译 ＋ 五类健全性检查，任何 LaTeX 项目都能用 |

**方法层面最值得带走的三条**

1. **「核验」必须按层拆开，并且分别声明哪层做了、哪层没做。**
   本包的事实层是可核验的，论证层不是；把这件事写在论文正文里，
   比假装两层都做了要可信得多。

2. **判据的强度决定了能抓到什么。**
   「编号能解析」抓不到「编号合法但内容无关」；
   「标题相似度 0.90」抓不到「0.92 的单词级篡改」。
   **设计核验器时，先问「我最怕的那种错误，这个判据能抓到吗」**，
   再倒推应该用什么判据。

3. **自动化的失败要用验证层修，不要用调阈值修。**
   Study B 的自动筛选查准 80%、查全 61.5%。
   调阈值只会把错误从假阳性挪到假阴性——**风险被挪动，没有被消除**。
   唯一的解法是加一层独立的验证，并把「这层抓到了什么」记录下来。

**给下一个做 C2 的同学的一句话**

> 这门挑战真正考的不是「你的论文多深」，而是
> **「你的每一个论断，读者能不能自己验一遍」**。
> 引用要能查到、数字要能复算、结论要标出边界——
> 再加上一条：**没做到的那部分，要自己先说**。
> 另外两条具体的：
> **① 本机没有 LaTeX 时，先用 `pipeline/00_setup_texlive.py`，别自己跟 installer 硬刚；
> ② 让 AI 列文献，第一条指令就要它带 arXiv 编号或 DOI，否则拿回来的东西没法核验。**
