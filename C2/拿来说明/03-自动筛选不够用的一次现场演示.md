# 拿来说明 03 · 自动筛选不够用：一次现场演示

> **一句话**：一个自动筛选器，查准 80%、查全 61.5%，**同时向两个方向出错**。
> 修复它的唯一有效方式是**加一层人工验证**，而不是调阈值——
> 调阈值只是把错误从假阳性挪到假阴性。

---

## 一、背景

论文要测「可复现评估」这条路线在语料里的实际落地程度：
**这 26 篇论文里，多少篇有公开的官方工件？**

「公开的官方工件」的严格定义是：
**仓库属于论文作者本人或本机构，且描述或 README 明确指向该论文。**

## 二、第一版：只看摘要（26.9%）

抓 arXiv abs 页摘要，用固定模式扫：

```python
ARTIFACT_PATTERNS = [
    (r"github\.com/[\w.\-]+/[\w.\-]+", "repo_url"),
    (r"code (?:is |are )?(?:publicly )?available", "code_available"),
    (r"open[- ]sourc\w+", "open_source"),
    (r"our code", "our_code"),
    (r"we release (?:our )?(?:code|data|model)", "we_release"),
    ...
]
```

产出 **7/26 = 26.9%**。

**这个数字明显偏低**——大量论文把仓库链接写在正文里而不是摘要里。
**直接报 26.9% 就是拿「摘要里提没提」冒充「有没有工件」。**
（这正是 C1 复盘批评过的「用容易实现的近似替掉字面要求」。）

## 三、第二版：加一路 GitHub 检索（假阳性爆炸）

用论文的「项目名」（标题冒号前的部分）查 GitHub 搜索 API。
第一版判定规则：

```python
"name_in_title": norm(it["name"]) in norm(title)   # 仓库名是不是标题的子串
```

产出：

```
cobbe2021gsm8k   → mlcommons/training               （标题里有 "Training"）
chen2026lectures → oxford-cs-deepnlp-2017/lectures  （标题里有 "Lectures"）
```

**规则太松**：短单词在长标题里总是子串。**假阳性。**

## 四、第三版：相似度 + 宁漏勿错（8/26）

```python
name_sim = _sim(项目名, 仓库名)
desc_sim = _sim(论文标题, 仓库描述)
qualified = (name_sim >= 0.90) or (desc_sim >= 0.70)
```

并**去掉「无冒号时退回第一个单词」**的逻辑——就是它让 `Training Verifiers...`
拿 "training" 去查的。

假阳性清零。**但假阴性还在，而且很明显。**

## 五、关键一步：对 near-miss 直接取证

看被**拒绝**的名单，有几条其实是对的：

```
chen2023pot  → TIGER-AI-Lab/Program-of-Thoughts    ns = 0.791   ← 被阈值卡掉
han2022pact  → jesse-michael-han/lean-step-public   ds = 0.659   ← 被阈值卡掉
```

**不猜，直接调 GitHub API 取仓库描述和 README 前 1200 字**：

```
TIGER-AI-Lab/Program-of-Thoughts
  desc   = "Data and Code for Program of Thoughts [TMLR 2023]"
  README = "This is code repository for the TMLR2023 paper
            [Program of Thoughts Prompting: ...](https://arxiv.org/abs/2211.12588)"

jesse-michael-han/lean-step-public
  desc   = "Proof artifact co-training for Lean"
```

**README 里直接写着 arXiv 编号 `2211.12588`，和论文对得上。两条都确认是官方仓库。**

## 六、定性：不能只靠自动，也不能只靠人工

最后定下来的结构：

```
自动检索（提名）  →  人工裁定（判定）  →  两者都留证据
      ↓                    ↓
  可复跑            可追责（每条写理由）
```

`artifact_adjudication.json` 里 26 条各有 `tier`、`repo`、`evidence`、`evidence_level`。

最需要小心的一条：

```
key   = xin2024deepseekprover
tier  = family          ← 不是 official
repo  = deepseek-ai/DeepSeek-Prover-V1.5
理由  = 这是 V1.5 的官方仓库，不是所引 V1 论文（arXiv:2405.14333）自身的工件。
        name_sim = 0.903 属于「同族不同篇」。
```

**如果没有这一步，这条会被算成「有工件」，把统计抬高。**

## 七、最终数字（论文表 3、表 4）

| 项 | 数 |
|---|---|
| 纳入测量（有 arXiv 号） | 26 |
| 排除（无 arXiv 号：3 篇 Nature + 1 篇 LNCS） | 4 |
| **有公开官方工件** | **13 / 26 = 50.0%** |
| 按范式：F 形式化 | 7/13 = 53.8% |
| 按范式：V 验证器 | 2/6 = 33.3% |
| 按范式：R 可复现评估 | 3/5 = 60.0% |

**自动 vs 人工裁定：**

| | 数 |
|---|---|
| 自动标记（两信号并集） | 10 |
| 真阳性 | 8 |
| 假阳性 | 2 |
| 假阴性 | 5 |
| **查准率** | **80.0%** |
| **查全率** | **61.5%** |

## 八、为什么这四个数字比「50%」更有价值

**自动筛选用论文自己的工具，把论文自己的论点演示了一遍：**

> 自动筛选本质是一个 $L_1 \to L_2$ 的归约（仓库页面 → 判定），
> 而这个归约恰好是不可靠的那一环——**同时向两个方向出错**。

更关键的是**修复方式**：

| 修法 | 结果 |
|---|---|
| 调松阈值 | 假阳性上升（`mlcommons/training` 这类又回来了） |
| 调紧阈值 | 假阴性上升（PoT 官方仓库又被卡掉） |
| **加一层人工验证** | 假阴性被补上，且**每一条都留有判断理由** |

**调阈值只是把残余风险从一头挪到另一头；加验证层才是真的减少它。**
这和论文第 3 节的核心主张是同一件事。

## 九、一个诚实的补充

这组数字**是意外得到的，不是设计出来的**。

写论文时发现表 3 的两列是手填的，而且口径（摘要筛选）和正文（两信号并集）不一致。
当时的修法有两条路：

1. 把正文改成和表一致（省事）；
2. **回脚本里把两个口径都算出来**。

选了第 2 条，才算出了查准/查全这组数。

**这说明「所有数字必须由脚本生成」这条规则不只是为了可复现——
它本身就会逼出结果。**

## 十、带走的三条

1. **单一信号的自动筛选，一定要报查准率和查全率，不能只报一个数。**
   只报「检出 8 条」会让人以为那就是全部。

2. **人工裁定的产物必须是「理由」，不是「勾选」。**
   每条写清 `repo` + `evidence` + `evidence_level`，才能被复核、被质疑。

3. **不要为了好数字调阈值。** 把自动与人工的**差距本身当成结果报出来**，
   比把差距抹平要诚实，也比抹平更有价值。
